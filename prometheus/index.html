라벨 셋 하나가
시간축 하나가 된다

Prometheus에서 중요한 단위는 “테이블의 행”이 아니라 series입니다. http_requests_total{job="api",instance="10.0.0.1"} 같은 라벨 셋 하나가 시간축 하나가 되고, 샘플은 WAL에 기록된 뒤 head chunk에 append됩니다. 시간이 지나면 이 head가 불변 block으로 굳고, block끼리 다시 compact됩니다.

01 / 용어부터

먼저 이 그림의 이름들

아래에서 계속 series · label postings · WAL · head chunk · block 이라는 말을 씁니다. Prometheus를 “시간별 로그 저장소”가 아니라 “라벨 인덱스가 붙은 append-only column chunk 저장소”로 보면 길이 훨씬 빨리 보입니다.

series 시간축
metric name + labels 전체가 같은 샘플들의 줄. label 값 하나만 달라도 완전히 다른 series 입니다.
sample 샘플
timestamp + value 한 쌍. Prometheus의 쓰기는 대부분 “기존 series 뒤에 sample append”입니다.
label postings
job="api" 같은 label pair 에서 series id 목록으로 가는 인덱스. selector 검색의 출발점입니다.
WAL
head에 쓰기 전에 append하는 복구 로그. 장애가 나면 WAL을 replay해서 최근 head를 다시 만듭니다.
chunk
한 series의 연속 샘플 묶음. timestamp는 delta-of-delta, value는 XOR 계열로 압축됩니다.
block
일정 시간 범위의 chunk와 index를 담은 불변 디렉터리. 처음에는 보통 2시간 block으로 생기고, 이후 compaction으로 커집니다.
기억할 규칙 두 개 ① 새 label set 은 새 series 를 만든다. ② 새 sample 은 기존 series 의 chunk 뒤에 append 된다. Prometheus의 성능 문제는 대부분 “샘플이 많다”보다 새 series 가 너무 많이 생긴다에서 터집니다.

03 / LABEL INDEX

카디널리티는 label set 개수다

Prometheus에서 샘플 수는 압축 chunk로 잘 버티지만, series 수는 메모리와 인덱스를 직접 키웁니다. 특히 user_id, request_id, trace_id처럼 값 종류가 계속 늘어나는 라벨은 새 series를 끝없이 만듭니다.

selector 는 postings 교집합이다

{job="api", __name__="http_requests_total"} job="api" postings = [#17, #18, #42] __name__="http_requests_total" = [#17, #42, #99] 교집합 = [#17, #42] // 그 다음에 시간 범위와 겹치는 chunk 만 읽는다

RDB의 복합 인덱스처럼 “하나의 정렬 키”를 타는 게 아니라, label pair마다 만들어진 series id 목록을 합칩니다. 그래서 라벨 이름과 값의 분포가 쿼리 비용을 바꿉니다.

나쁜 라벨 하나가 만드는 폭발

라벨값 개수결과
job10서비스 단위. 안정적이라 좋다
instance500타깃 단위. 보통 필요하다
method6낮은 cardinality
user_id1,000,000각 사용자마다 별도 series. 운영 사고 후보

04 / BLOCKS

최근은 head, 과거는 block

Prometheus는 최근 데이터를 head에 append하다가 일정 범위가 차면 불변 block으로 저장합니다. block은 한 번 만들어지면 수정하지 않고, 삭제는 tombstone으로 표시했다가 compaction 때 정리합니다.

파일/영역담당자료구조 관점
head최근 쓰기메모리의 series map + active chunk. append에 최적화
wal/복구series와 sample record를 순서대로 append. restart 때 replay
chunks/샘플 저장series별 연속 샘플 묶음. XOR 계열 압축으로 timestamp/value를 작게 저장
indexlabel 검색symbol table, label index, postings, series metadata가 들어 있는 block-local 인덱스
tombstones삭제 표시block은 불변이라 지운 범위만 표시. compaction 때 실제 제거
meta.jsonblock 메타ULID, minTime/maxTime, compaction level, sources 기록

왜 chunk 압축이 잘 되는가

  • scrape 간격은 보통 일정하다 → timestamp delta-of-delta가 0에 가까움
  • 카운터와 게이지는 직전 값과 비슷하게 움직인다 → value XOR가 작음
  • series별로 따로 묶어야 같은 패턴이 이어진다

그래서 Prometheus는 행 단위 이벤트 로그보다 “동일 라벨 셋의 규칙적인 숫자 흐름”에 훨씬 강합니다.

Compaction 이 하는 일

  • 작은 block을 더 긴 시간 범위 block으로 병합
  • 삭제 표시된 샘플 범위를 실제로 제거
  • 쿼리가 열어야 할 block 수를 줄임
  • 대신 백그라운드 디스크 I/O를 쓴다

RDB의 page split과 달리 과거 block은 제자리 수정하지 않습니다. 새 block을 만들고, 성공하면 이전 block을 버립니다.

05 / IN PRACTICE

이 구조가 운영에서 드러나는 순간

Prometheus는 이벤트 저장소가 아니다

“요청 1건 = sample 1개”처럼 쓰면 series와 sample 패턴이 모두 망가집니다. 이벤트는 로그/트레이싱/OLAP으로 보내고, Prometheus에는 집계된 숫자를 넣는 편이 맞습니다.

  • 좋음: http_requests_total{job, method, code}
  • 위험: http_request{request_id, user_id, raw_path}

recording rule 은 materialized series

매번 비싼 PromQL을 계산하는 대신, 결과를 새 series로 미리 저장합니다. ClickHouse의 materialized view와 비슷한 감각입니다.

  • 대시보드 반복 쿼리 비용 감소
  • 알림 규칙의 지연과 부하 완화
  • 대신 저장할 series가 늘어난다는 비용이 생김

remote write 가 필요한 지점

Prometheus 로컬 TSDB는 빠른 최근 관측에 강합니다. 장기 보관, 전역 쿼리, 다중 클러스터 집계가 필요하면 Thanos, Mimir, Cortex 같은 장기 저장 계층으로 remote write를 붙입니다.

소스에서 확인할 키워드

  • tsdb.Head — 최근 series와 chunks
  • index.Postings — label pair에서 series ref 목록
  • chunks.Meta — chunk 시간 범위와 참조
  • LeveledCompactor — block compaction 정책
ClickHouse 페이지와 이어서 보기 Prometheus는 라벨로 series를 찾고 시간 범위 chunk를 읽는 구조입니다. ClickHouse는 정렬 키로 granule을 줄이고 필요한 컬럼만 읽는 구조입니다. 둘 다 시계열을 다루지만, Prometheus는 관측 지표의 최근 조회에, ClickHouse는 큰 범위의 분석 질의에 더 잘 맞습니다.

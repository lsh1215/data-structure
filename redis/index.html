01 / 용어부터

먼저 이 그림의 이름들

아래에서 계속 해시 · 버킷 · 체인 · dictEntry · load factor 라는 말을 씁니다. Redis 소스에 그대로 나오는 이름이라 한 번만 익혀두면 코드를 열었을 때도 길을 잃지 않습니다.

dict 딕셔너리
Redis의 키-값 저장소 본체. 버킷 배열 + 그 안에 매달린 엔트리들을 합쳐 부르는 이름입니다.
해시 함수 hash
문자열 키를 고정 길이 숫자로 바꾸는 함수. 같은 키는 항상 같은 숫자가 나옵니다.
버킷 bucket · slot
배열의 칸 하나. 해시값으로 몇 번 칸인지 정합니다. 칸에는 값이 아니라 첫 엔트리의 주소만 들어 있습니다.
sizemask
size − 1. 배열 크기가 항상 2의 거듭제곱이라 해시값 & sizemask 만으로 칸 번호가 나옵니다.
dictEntry 엔트리
키 하나 · 값 하나 · 다음 엔트리를 가리키는 포인터를 담은 24바이트짜리 구조체.
충돌 · 체인 collision · chaining
서로 다른 키가 같은 칸에 떨어지는 것. 그럴 땐 엔트리를 줄줄이 매달아(체인) 해결합니다.
load factor 적재율
used ÷ size. 저장된 엔트리 수를 칸 수로 나눈 값이며, 이 값이 곧 평균 체인 길이입니다. 1을 넘으면 배열을 키웁니다.
리해싱 rehash
배열을 두 배로 늘리고 모든 엔트리의 칸 번호를 다시 계산해 옮기는 것. Redis는 이걸 한 번에 안 하고 나눠서 합니다.
기억할 규칙 두 개 ① 키를 해시해서 칸 번호를 구하고, 그 칸의 체인을 훑어 키를 찾는다. ② 체인이 길어지면 느려지므로 칸 수를 늘려(리해싱) 체인을 짧게 유지한다. 아래 애니메이션은 이 두 문장의 반복입니다.

03 / ANATOMY

dict · dictht · dictEntry

위 그림의 각 요소가 실제 C 구조체의 어느 필드인지 짚어봅니다. 이름만 알면 소스를 열었을 때 길을 잃지 않습니다.

구조체 (Redis 6 기준)
typedef struct dictEntry { void *key; // SDS 문자열 포인터 union { void *val; // robj 포인터 uint64_t u64; int64_t s64; double d; } v; struct dictEntry *next; // 같은 버킷의 다음 엔트리 } dictEntry; // 64bit 에서 24 bytes typedef struct dictht { dictEntry **table; // 버킷 배열 (포인터의 배열) unsigned long size; // 항상 2의 거듭제곱 unsigned long sizemask; // size - 1 unsigned long used; // 저장된 엔트리 수 } dictht; typedef struct dict { dictType *type; dictht ht[2]; // [0]=현재, [1]=리해싱 대상 long rehashidx; // -1 이면 리해싱 중 아님 int16_t pauserehash; } dict;

Redis 7 부터는 dictht 구조체가 사라지고 dict 안에 dictEntry **ht_table[2], ht_used[2], ht_size_exp[2] 로 평탄화되었습니다. 개념은 그대로입니다.

왜 size 는 항상 2의 거듭제곱인가

버킷 인덱스를 구할 때 나눗셈(%)은 CPU에서 수십 사이클이 드는 비싼 연산입니다. 크기가 2ⁿ이면 sizemask = size − 1 이 0b0111…1 형태가 되어 비트 AND 한 번으로 끝납니다.

size = 16 = 0b00010000 sizemask = 16 − 1 = 0b00001111 hash = 0x3f2a1b9c idx = hash & sizemask = ...10011100 & 0b1111 = 12 // 하위 4비트만 남는다

덤으로, 크기를 2배로 늘리면 각 엔트리는 제자리에 남거나 정확히 size 만큼 뒤로 이동합니다. 비트 하나가 더 보이게 되는 것뿐이기 때문입니다. 리해싱이 예측 가능한 이유입니다.

  • 해시가 균등하다면 체인 평균 길이 = load factor
  • load factor 를 1 근처로 유지 → 평균 O(1)
  • 최악은 모든 키가 한 버킷 → O(N). 그래서 SipHash + 랜덤 시드로 해시 충돌 공격을 막는다

04 / REHASH

왜 한 번에 옮기지 않는가

Redis 는 명령을 한 스레드로 처리합니다. 1000만 개의 키를 새 테이블로 한 번에 복사하면 그 몇 초 동안 서버 전체가 멈춥니다. 그래서 이사를 한 버킷씩 나눠서 합니다.

이사 규칙 4가지

  • 조회는 두 테이블 모두 — ht[0] 에 없으면 ht[1] 도 본다
  • 삽입은 ht[1] 에만 — 그래야 ht[0] 이 단조 감소해서 언젠가 끝난다
  • rehashidx 앞쪽 버킷은 이미 비어 있다 — 그 구간은 볼 필요가 없다
  • ht[0].used 가 0 이 되면 ht[0] 을 해제하고 ht[1] 을 ht[0] 으로 승격
dictRehashStep(d) // 명령이 올 때마다 1 버킷 ├ dictAddRaw() ├ dictFind() └ dictDelete() databasesCron() // 유휴 시간에 1ms 동안 └ incrementallyRehash()

빈 버킷만 계속 나오는 경우를 대비해 한 번에 최대 n×10 개의 빈 버킷만 건너뛰고 중단합니다. 어떤 명령도 리해싱 때문에 오래 붙잡히지 않게 하는 장치입니다.

BGSAVE 중에는 왜 확장을 미루는가

RDB 저장이나 AOF 재작성은 fork() 로 자식 프로세스를 만듭니다. 부모와 자식은 물리 메모리를 공유(Copy-on-Write)하다가, 부모가 페이지를 수정하는 순간에만 복사합니다.

  • 리해싱은 모든 엔트리를 건드린다 → 거의 모든 페이지가 복사된다
  • 메모리 사용량이 순간적으로 2배로 튄다 → OOM 위험
  • 그래서 dict_can_resize = 0 으로 확장을 미룬다
  • 단, load factor 가 dict_force_resize_ratio(5) 를 넘으면 체인이 너무 길어지므로 강제 확장

위 시각화에서 BGSAVE 중 체크박스를 켜고 계속 넣어보면 이 규칙이 그대로 재현됩니다.

SCAN 이 안전한 이유도 여기 있다 리해싱 중에는 커서를 그냥 0,1,2… 로 늘리면 엔트리를 빠뜨리거나 중복해서 보게 됩니다. Redis 의 SCAN 은 커서를 비트를 거꾸로 뒤집어 증가(reverse binary iteration)시켜, 테이블 크기가 바뀌어도 이미 본 원소는 다시 안 보고 처음부터 있던 원소는 반드시 보게 만듭니다.
05 / SKIPLIST

ZSET 은 왜 트리가 아니라 skiplist 인가

정렬이 필요한 ZSET 은 해시로 안 됩니다. 그렇다고 균형 트리(red-black, AVL)를 쓰지도 않습니다. Redis 는 동전을 던져 층을 정하는 skiplist 를 씁니다. 회전(rotation)이 없어 코드가 짧고, 범위 질의가 쉽기 때문입니다.

레벨 추첨 결과

레벨은 확률로 정해진다

int zslRandomLevel(void) { int level = 1; while (random() < 0.25 && level < 32) level += 1; return level; }
  • 레벨 L 이 될 확률 = 0.25^(L−1) × 0.75
  • 75%는 레벨 1, 약 19%는 레벨 2, 약 4.7%는 레벨 3…
  • 평균 레벨 = 1/(1−p) = 1.33 → 노드당 포인터 1.33개
  • 기대 탐색 비용 = O(log1/p N) = O(log₄ N)

회전도, 재균형도 없습니다. 그냥 동전을 던지고 연결 리스트에 끼워 넣을 뿐인데 기대값으로 균형이 잡힙니다.

span 이 있어서 ZRANK 가 빠르다

각 forward 포인터에는 몇 칸을 건너뛰는지(span)가 함께 저장됩니다. 위 그림의 각 셀에 적힌 숫자가 그것입니다.

  • 탐색하며 span 을 더하면 그 원소가 몇 번째인지 바로 나온다 → ZRANK O(log N)
  • 순위로 자르기도 가능 → ZRANGE key 0 9 가 빠른 이유
  • ZSET 은 skiplist + dict 두 개를 같이 유지한다 → ZSCORE 는 dict 로 O(1)

즉 ZSET 하나는 “정렬을 위한 skiplist”와 “멤버→점수 조회를 위한 해시” 두 자료구조의 합성입니다. 메모리를 더 쓰는 대신 두 종류의 질의를 모두 빠르게 만듭니다.

06 / ENCODING

작을 때는 해시를 쓰지 않는다

원소가 몇 개 안 되면 Redis 는 해시 테이블 대신 연속된 바이트 배열(listpack)에 그냥 쭉 저장하고 선형 탐색합니다. O(N)이 O(1)보다 빠른 구간이 실제로 존재하기 때문입니다 — 캐시 때문입니다.

O(N)이 O(1)을 이기는 구간

  • listpack 은 연속 메모리 — 캐시 라인 한두 번이면 다 읽는다
  • dict 는 해시 계산 + 포인터 추적 → 캐시 미스가 발생한다
  • 원소 128개 정도까지는 그냥 훑는 게 더 빠르고, 메모리도 훨씬 적게 쓴다

그래서 “작은 해시를 많이” 쓰는 패턴(user:1 필드 5개짜리 해시 100만 개)은 메모리 효율이 아주 좋습니다. 임계값을 넘기면 갑자기 메모리가 몇 배로 뜁니다.

한 번 커지면 되돌아가지 않는다

listpack → hashtable 전환은 단방향입니다. 원소를 다시 지워도 인코딩은 그대로 hashtable 로 남습니다.

  • 매번 되돌리는 비용이 크고, 경계에서 진동(thrashing)이 생기기 때문
  • 확인: OBJECT ENCODING key
  • 메모리를 되찾으려면 키를 새로 만들어야 한다

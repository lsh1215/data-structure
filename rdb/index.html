디스크 위의 트리는
이렇게 자란다

PostgreSQL의 CREATE INDEX, MySQL InnoDB의 클러스터드 인덱스는 모두 B-Tree 계열입니다. 키를 하나 넣을 때마다 노드가 어떻게 차오르고, 언제 쪼개지며, 트리가 언제 한 층 높아지는지를 직접 넣어보면서 확인하세요. 아래에서는 log의 밑이 왜 2가 아닌지를 수식으로 유도합니다.

01 / VISUALIZE

한 키씩 넣어보기

한 개의 상자 = 디스크 한 페이지입니다. 페이지가 담을 수 있는 키 개수를 넘기면 오버플로 가 발생하고, 중앙 키가 부모로 올라가면서 노드가 둘로 갈라집니다. 부모까지 꽉 차면 그 위로 계속 전파되고, 루트가 갈라지는 순간에만 트리의 높이가 1 증가합니다.

02 / COMPARE

B-Tree와 B+Tree는 무엇이 다른가

위 시각화에서 모드를 바꾸면 바로 보입니다. B-Tree는 내부 노드에도 실제 데이터가 있고, B+Tree는 데이터가 전부 리프에만 있으며 내부 노드의 키는 길 안내용 이정표(separator)일 뿐입니다.

항목B-TreeB+Tree (실제 DB 인덱스)
데이터 위치내부 노드 + 리프 모두리프에만
내부 노드 키실제 키(값과 함께)구분자(separator)만 — 값이 없다
한 페이지 fanout키+값+포인터 → 작다키+포인터만 → 크다 (높이가 낮아짐)
단건 조회운 좋으면 루트에서 바로 끝항상 리프까지 (대신 높이가 낮음)
범위 조회중위 순회 — 위아래 왕복, 랜덤 I/O리프 링크 순차 스캔 — O(log N + k/b)
정렬 결과순회 필요리프 순서 = 정렬 순서 (ORDER BY 생략 가능)
분할 시 중앙 키위로 이동 (push-up, 리프에서 사라짐)위로 복사 (copy-up, 리프에도 남음)
쓰는 곳일부 파일시스템, MongoDB WiredTiger 등InnoDB, PostgreSQL, Oracle, SQL Server

왜 DB는 결국 B+Tree인가

페이지 크기가 고정되어 있다면 한 페이지에 담긴 엔트리 수가 곧 fanout이고, fanout이 곧 log의 밑입니다.

  • 내부 노드에서 값(row)을 빼면 엔트리가 작아져 fanout이 몇 배로 커진다
  • fanout이 커지면 같은 N을 담아도 높이가 낮아진다 → 디스크 I/O 감소
  • 리프를 링크드 리스트로 엮으면 범위 스캔이 순차 I/O가 된다

즉 B+Tree는 “탐색을 빠르게” 만든 구조가 아니라 “디스크를 덜 만지게” 만든 구조입니다.

내부 노드의 키는 값이 아니다

B+Tree에서 값을 지워도 내부 노드에 그 숫자가 남아 있는 경우가 있습니다. 위 시각화에서 직접 만들어볼 수 있습니다.

  • 내부 노드의 42는 “42 이상은 오른쪽”이라는 이정표
  • 실제 42가 삭제돼도 이정표는 그대로 둬도 탐색은 여전히 정확하다
  • 탐색은 항상 리프까지 내려간 뒤에야 존재 여부를 판정한다

이 성질 때문에 B+Tree의 삭제는 “리프만 정리하면 되는” 값싼 연산이 됩니다.

03 / MATH

log의 밑은 무엇이고, 왜 그런가

“B-Tree는 O(log N)” 이라는 말은 절반만 맞습니다. 중요한 건 밑(base)입니다. 밑이 2인지 500인지에 따라 실제 디스크 접근 횟수가 27번과 3번으로 갈립니다. 아래에서 상한과 하한을 직접 유도합니다.

기호 정의
  • m — 한 노드(=한 페이지)가 가질 수 있는 최대 자식 수. 차수(order) 또는 fanout
  • t = ⌈m/2⌉ — 루트를 제외한 노드의 최소 자식 수 (B-Tree의 균형 규칙)
  • N — 인덱스에 저장된 키 개수
  • h — 루트에서 리프까지의 레벨 수. 루트만 있으면 h = 1

① 높이의 하한 — 가장 꽉 채웠을 때

모든 노드가 최대로 찼다고 가정합니다. 레벨 i(루트가 0)의 노드 수는 최대 m^i개이고, 각 노드는 최대 m−1개의 키를 가집니다. 따라서 높이 h인 트리가 담을 수 있는 키의 최대치는:

// 등비수열의 합 N ≤ Σi=0h−1 mi · (m−1) = (m−1) · (mh − 1) / (m − 1) = mh − 1 // 정리하면 mh ≥ N + 1 h ≥ logm(N + 1)

② 높이의 상한 — 가장 헐렁할 때

B-Tree 규칙상 루트를 제외한 모든 노드는 최소 t = ⌈m/2⌉개의 자식(= t−1개의 키)을 가져야 합니다. 루트는 최소 2개의 자식만 있으면 됩니다. 가장 적게 채운 트리를 세어보면:

// 레벨 i(≥1)의 최소 노드 수: 2 · t^(i−1) N ≥ 1 + Σi=1h−1 2·ti−1·(t−1) = 1 + 2(t−1) · (th−1 − 1)/(t − 1) = 2·th−1 − 1 // 정리하면 th−1 ≤ (N + 1) / 2 h ≤ logt( (N + 1) / 2 ) + 1
결론 logm(N+1) ≤ h ≤ log⌈m/2⌉((N+1)/2) + 1 → 상한과 하한 모두 밑이 m 계열의 로그입니다. 즉 h = Θ(logm N). 위 시각화의 “이론 높이 범위” 값이 바로 이 두 식이며, 실제 트리 높이가 항상 그 사이에 들어가는 것을 확인할 수 있습니다.

③ 왜 밑이 2가 아니라 fanout인가 — 비용 모델의 문제

알고리즘 교과서의 이진 트리는 “비교 1회”를 비용 단위로 삼습니다. 하지만 데이터베이스의 비용 단위는 디스크 I/O 1회입니다.

  • 디스크/SSD는 바이트가 아니라 블록(페이지) 단위로 읽는다 — 8바이트를 읽든 16KB를 읽든 I/O는 1회
  • 그러므로 “한 번 읽을 때 최대한 많은 키를 가져오는 것”이 이득이다 → 노드 크기 = 페이지 크기
  • 노드 하나에 키가 m−1개 들어가면 분기 수가 m이 되고, 트리 높이는 logmN이 된다

밑 변환 공식을 쓰면 이진 트리와의 차이가 정확히 보입니다:

logm N = log2 N / log2 m // 즉 이진 탐색 트리보다 정확히 log₂(m) 배 낮다 m = 500 → log2500 ≈ 8.97 // 높이가 약 1/9 N = 108 일 때 이진 트리 : log2108 ≈ 26.6 → 27회 I/O B+Tree : log500108 = 26.6 / 8.97 ≈ 3.0 → 3회 I/O

④ 함정: CPU 비교 횟수는 줄어들지 않는다

노드 안의 키는 정렬된 배열이므로 이진 탐색을 합니다. 노드당 log₂m번 비교하고, 노드를 logmN개 방문하므로:

총 비교 횟수 = h × log2m = logmN × log2m = (log2N / log2m) × log2m = log2N // 이진 트리와 동일!

B-Tree는 비교 횟수를 줄이는 자료구조가 아니라 I/O 횟수를 줄이는 자료구조입니다. 그래서 모든 데이터가 이미 메모리에 있는 Redis 같은 시스템은 B-Tree를 쓸 이유가 없고, 해시 테이블을 씁니다.

⑤ 분할 비용의 amortized 분석

분할은 노드가 꽉 찼을 때만 일어납니다. 분할 직후 두 노드는 각각 약 m/2개의 키를 가지므로, 같은 노드가 다시 분할되려면 최소 m/2번의 삽입이 더 필요합니다.

삽입당 평균 분할 횟수 ≤ 2/m = O(1/m) // m = 500 이면 250번 삽입에 1번꼴 삽입 비용 = O(logfN) I/O + amortized O(1) 분할

그래서 “인덱스가 많으면 INSERT가 느려진다”의 주된 원인은 분할 자체보다 인덱스마다 별도의 루트→리프 경로를 갱신해야 하는 데 있습니다.

⑥ 실제로는 I/O가 h번보다 적다

상위 레벨은 노드 수가 적어 버퍼 풀(메모리)에 거의 항상 올라와 있습니다.

  • 루트 1개 — 사실상 100% 캐시 히트
  • 레벨 1은 수천 개 — 수십 MB면 전부 캐시
  • 리프만 수백만 개 — 여기서 실제 디스크 I/O 발생

따라서 h = 4인 인덱스라도 실제 디스크 접근은 보통 1~2회입니다. 그래서 innodb_buffer_pool_size 튜닝이 인덱스 설계만큼 중요합니다.

04 / IN PRACTICE

이 모양이 SQL로 드러나는 순간

인덱스 규칙을 외우는 대신, 위에서 본 트리 모양으로 설명하면 전부 자명해집니다.

LIKE 'abc%' 는 타고 '%abc' 는 못 탄다

인덱스의 정렬 기준은 키의 맨 앞부터입니다. 내부 노드의 이정표는 “앞에서부터 비교했을 때 이쪽/저쪽”만 알려줍니다.

  • 'abc%' — 시작점을 특정할 수 있다 → 리프 한 지점부터 순차 스캔
  • '%abc' — 어느 리프에서 시작할지 알 수 없다 → 전체 스캔

복합 인덱스의 왼쪽 접두사 규칙

INDEX(a, b, c)는 (a,b,c) 튜플을 하나의 키로 정렬한 트리입니다.

  • WHERE a=1 AND b=2 — a로 좁힌 뒤 그 안에서 b도 정렬돼 있다 → OK
  • WHERE b=2 — b는 a가 다른 구간마다 흩어져 있다 → 시작점 없음

랜덤 UUID를 PK로 쓰면 벌어지는 일

위 시각화에서 랜덤 값을 계속 넣어보면 트리 곳곳에서 분할이 터집니다. InnoDB는 PK가 곧 데이터이므로(클러스터드) 이 분할은 데이터 페이지 분할입니다.

  • 페이지 분할 폭증 → 채움률 하락 → 같은 데이터에 더 많은 페이지
  • 쓰기 지점이 흩어짐 → 버퍼 풀 히트율 하락
  • 대안: AUTO_INCREMENT, ULID, UUIDv7 처럼 시간 정렬된 키

커버링 인덱스가 빠른 이유

세컨더리 인덱스의 리프에는 PK가 들어 있습니다. 필요한 컬럼이 인덱스에 없으면 PK로 클러스터드 인덱스를 다시 타야 합니다 (bookmark lookup).

  • 일반: 세컨더리 h회 + 클러스터드 h회 × 결과 행 수
  • 커버링: 세컨더리 h회 + 리프 순차 스캔으로 끝
한 줄 요약 B+Tree의 시간복잡도는 O(logf N)이고, 여기서 f는 페이지 하나에 들어가는 엔트리 수입니다. 인덱스 튜닝의 대부분은 결국 “f를 키우고 h를 줄이는 일” — 즉 키를 짧게, 페이지를 꽉 차게, 삽입을 한쪽 끝으로 몰아주는 일입니다.

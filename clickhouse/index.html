용어 INSERT와 쿼리 희소 인덱스 MergeTree 실무 연결
Columnar OLAP · Sparse Index

한 행을 찾지 말고
읽을 granule을 줄인다

ClickHouse의 MergeTree는 RDB처럼 row를 하나씩 B+Tree에 끼워 넣지 않습니다. INSERT batch를 ORDER BY 키로 정렬된 불변 part로 쓰고, 대략 granule마다 하나씩 저장한 sparse primary index mark로 “읽을 가능성이 있는 범위”만 고릅니다. Primary key는 유니크 제약이 아니라 데이터를 저장하는 순서입니다.

01 / 용어부터

먼저 이 그림의 이름들

아래에서 계속 part · primary key · granule · mark · merge 라는 말을 씁니다. ClickHouse는 “정렬된 컬럼 파일 묶음”과 “희소한 이정표”로 큰 범위 쿼리를 빨리 만듭니다.

part data part
INSERT batch가 디스크에 저장된 불변 파일 묶음. 각 part는 독립적으로 정렬돼 있고 나중에 background merge로 합쳐집니다.
ORDER BY sorting key
part 내부 행의 저장 순서. ClickHouse에서 primary key는 보통 이 정렬 키의 prefix입니다.
granule
인덱스가 가리키는 최소 읽기 단위. 기본 index_granularity 8192행 근처로 생각하면 됩니다.
mark
granule 첫 행의 primary key와 컬럼 파일 offset. sparse index는 모든 행이 아니라 mark만 들고 있습니다.
primary index
정렬 키 위의 희소 인덱스. 유니크 보장이 아니라 granule pruning을 위한 이정표입니다.
merge
작은 part 여러 개를 더 큰 정렬 part로 합치는 백그라운드 작업. part 수와 중복 읽기 비용을 줄입니다.
기억할 규칙 두 개 ① ClickHouse primary key는 “중복 금지”가 아니라 정렬과 스킵의 기준이다. ② mark는 모든 행이 아니라 granule마다 하나라서 정확한 한 행이 아니라 읽을 범위를 줄인다.

03 / SPARSE INDEX

왜 모든 row를 인덱싱하지 않는가

분석 쿼리는 보통 한 행이 아니라 수백만 행을 읽습니다. 그래서 ClickHouse는 row마다 포인터를 두는 대신 granule마다 mark 하나를 두고, 읽을 범위를 대략 줄인 뒤 컬럼 파일을 순차적으로 읽습니다.

index_granularity 감각

기본 granule ≈ 8192 rows 1억 rows / 8192 ≈ 12,208 marks // 모든 row 포인터 대신 mark 1만여 개면 primary index 전체를 메모리에 두기 쉽다 WHERE service='api' → 정렬 키 prefix 로 mark 범위 선택 → 선택된 granule 의 필요한 컬럼만 읽음

granule 안에서는 결국 읽고 필터링합니다. 그래서 정렬 키가 쿼리 패턴과 맞으면 극적으로 줄고, 맞지 않으면 넓게 읽습니다.

04 / MERGETREE

part가 많아지면 배경에서 합친다

INSERT는 빠르게 새 part를 만들지만, part가 너무 많으면 쿼리는 part마다 index를 열어야 합니다. MergeTree라는 이름 그대로, 같은 partition의 작은 part들을 백그라운드에서 더 큰 정렬 part로 합칩니다.

쓰기 경로

  • INSERT batch 수신
  • partition key 별로 나눔
  • 각 partition 안에서 ORDER BY 키로 정렬
  • 컬럼 파일, marks, primary index, checksums를 새 part로 작성
  • 메타데이터를 교체해 part를 보이게 함

작은 INSERT를 너무 자주 보내면 작은 part가 많아져 merge 부하가 커집니다. ClickHouse가 batch insert를 좋아하는 이유입니다.

삭제와 업데이트는 “새 part 쓰기”

MergeTree part는 불변에 가깝게 다뤄집니다. DELETE/UPDATE mutation은 조건에 맞는 part를 다시 쓰는 작업에 가깝고, 그래서 OLTP처럼 자주 수정하는 워크로드와 맞지 않습니다.

  • 대량 append와 분석 읽기에는 강함
  • 단건 update/delete에는 비쌈
  • 실시간 정정이 많으면 ReplacingMergeTree 같은 엔진 설계가 필요

05 / IN PRACTICE

ORDER BY를 고를 때 보는 것

자주 거르는 조건을 앞에 둔다

ORDER BY (service, day, ts)라면 service='api'와 day 범위가 있을 때 granule pruning이 잘 됩니다.

  • 좋음: WHERE service='api' AND day=today()
  • 약함: WHERE status=500만 있는 쿼리
  • 해결: status가 핵심이면 정렬 키나 skipping index를 재검토

카디널리티가 낮은 것부터 무조건은 아니다

낮은 cardinality 컬럼을 앞에 두면 압축과 pruning에 유리할 수 있지만, 너무 낮으면 큰 덩어리로만 나뉩니다. 실제 쿼리의 WHERE, GROUP BY, ORDER BY 패턴이 우선입니다.

SELECT 컬럼 수가 곧 I/O다

컬럼 저장소이므로 SELECT *는 진짜로 모든 컬럼 파일을 읽는 쪽에 가깝습니다. 대시보드와 배치 쿼리에서는 필요한 컬럼만 명시하는 습관이 성능에 바로 이어집니다.

Prometheus와 같이 쓸 때

Prometheus는 서비스 상태를 빠르게 보는 데 좋고, ClickHouse는 오래된 고해상도 이벤트/메트릭을 넓게 분석하는 데 좋습니다. 지표는 Prometheus, 원천 이벤트와 장기 분석은 ClickHouse로 나누면 각자의 자료구조가 잘 살아납니다.

한 줄 요약 ClickHouse 튜닝의 첫 질문은 “인덱스를 탔나?”가 아니라 “ORDER BY 덕분에 몇 개 granule을 건너뛰었나?”입니다. 읽은 rows와 marks를 줄이고, 필요한 컬럼만 읽게 만들면 분석 쿼리가 빨라집니다.

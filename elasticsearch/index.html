02 / SCORING

BM25 — 왜 이 문서가 1등인가

검색 결과 순서는 마법이 아니라 하나의 수식입니다. 위 시각화에서 검색하면 문서마다 이 계산이 그대로 찍힙니다.

score(D, Q) = Σt∈Q IDF(t) · tf(t,D) · (k₁ + 1) ───────────────────────────── tf(t,D) + k₁ · (1 − b + b · dl/avgdl) IDF(t) = ln( 1 + (N − df(t) + 0.5) / (df(t) + 0.5) ) // 기본 파라미터 k₁ = 1.2 // tf 포화 속도. 클수록 반복 등장을 더 인정 b = 0.75 // 문서 길이 정규화 강도. 0이면 길이 무시

IDF — 흔한 단어는 깎는다

df 가 클수록 (= 많은 문서에 등장할수록) 값이 작아집니다. 모든 문서에 나오는 단어는 변별력이 없으니까요.

  • N=1000, df=1 → IDF ≈ 6.5
  • N=1000, df=500 → IDF ≈ 0.69
  • +0.5 와 ln(1+…) 은 df가 클 때 음수가 되는 걸 막는 보정

tf 포화 — 10번이 2번의 5배는 아니다

분모에 tf 가 있어 tf가 커질수록 증가폭이 줄고 k₁+1 에 수렴합니다.

  • tf 1 → 2 : 점수 크게 상승
  • tf 10 → 20 : 거의 변화 없음
  • TF-IDF의 “키워드 도배” 취약점을 막는 장치

길이 정규화 — 긴 문서 불리

dl/avgdl 이 1보다 크면 (평균보다 긴 문서) 분모가 커져 점수가 깎입니다.

  • 긴 문서는 우연히 단어를 포함할 확률이 높기 때문
  • b=0 이면 길이를 완전히 무시
  • 제목 필드처럼 짧은 필드는 b를 낮추기도 한다
TF-IDF 와의 차이 TF-IDF 는 tf × idf 로 tf 가 선형으로 반영되고 문서 길이를 직접 다루지 않습니다. BM25 는 tf 포화와 길이 정규화를 확률 모델에서 유도해 넣은 것이고, 그래서 Lucene 6부터 기본 유사도가 BM25 로 바뀌었습니다.
03 / SEGMENT

색인했는데 왜 바로 검색이 안 되는가

Lucene 세그먼트는 한 번 쓰면 못 고치는(immutable) 파일입니다. 그래서 색인은 “버퍼에 모았다가 → 세그먼트를 새로 만들고 → 나중에 합치는” 방식으로 동작합니다.

왜 이런 구조인가
  • 불변이라 락 없이 동시 읽기가 가능하다
  • 불변이라 OS 캐시에 그대로 올려둘 수 있다
  • 대신 삭제·수정은 “표시”만 하고 merge 때 정리
  • 세그먼트가 많으면 검색이 느려진다 (모두 뒤져야 하므로)

refresh vs flush vs commit

동작주기결과
refresh1초 (기본)버퍼 → 새 세그먼트. 이때부터 검색됨. fsync 는 안 함
flush30분 / 512MBfsync + translog 비움. Lucene commit
merge백그라운드작은 세그먼트들을 합치고 삭제 문서를 실제로 제거

대량 색인 작업에서는 index.refresh_interval 을 -1 로 껐다가 끝나고 되돌리면 세그먼트 생성과 병합 비용이 크게 줄어 처리량이 몇 배 올라갑니다.

“업데이트”라는 것은 없다

문서를 수정하면 Elasticsearch 는 내부적으로 이렇게 합니다.

  • 기존 문서를 삭제 표시(.del 비트)
  • 수정된 내용을 새 문서로 색인 (버전 +1)
  • merge 될 때 옛 문서가 물리적으로 사라짐

그래서 잦은 부분 업데이트는 세그먼트를 부풀리고 merge 부하를 키웁니다. 자주 바뀌는 필드는 아예 다른 저장소에 두거나, 별도 인덱스로 분리하는 편이 낫습니다.

05 / IN PRACTICE

이 구조가 설정으로 드러나는 순간

text vs keyword

  • text — analyzer 를 거쳐 토큰으로 쪼갠다. 전문 검색용, 정렬·집계 불가
  • keyword — 통째로 하나의 term. 정확 일치·정렬·집계용
  • 둘 다 필요하면 multi-field 로 title + title.keyword

“정렬이 이상해요”의 90%는 text 필드로 정렬을 시도한 경우입니다. 토큰으로 쪼개져 있으니 당연합니다.

deep pagination 이 위험한 이유

from=10000&size=10 은 각 샤드에서 10010건을 모두 정렬해 코디네이터로 보내야 합니다.

  • 샤드 10개면 100,100건이 메모리에 모인다
  • 대안: search_after (마지막 정렬값 기준 이어받기)
  • 전량 추출은 scroll 대신 PIT + search_after

샤드 수를 늘린다고 빨라지지 않는다

각 샤드는 독립적인 Lucene 인덱스입니다. 즉 세그먼트도, term dictionary 도 샤드마다 따로 있습니다.

  • 샤드가 많으면 병렬성은 오르지만 고정 비용도 그만큼 늘어난다
  • IDF 도 샤드별로 계산되어 문서가 적으면 점수가 흔들린다 (dfs_query_then_fetch)
  • 경험칙: 샤드 하나당 10~50GB, 노드 힙 1GB당 샤드 20개 이하

한국어는 analyzer 가 전부다

영어는 공백으로 잘라도 그럭저럭 되지만 한국어는 조사가 붙어 있어 표준 토크나이저로는 “검색이”와 “검색을”이 다른 term 이 됩니다.

  • 형태소 분석기(nori, arirang)로 어간을 뽑아야 한다
  • 동의어·불용어 사전은 색인·검색 양쪽에 같이 적용
  • 사전을 바꾸면 기존 세그먼트는 그대로 → 재색인이 필요하다
세 페이지를 잇는 한 문장 B+Tree 는 디스크 I/O 횟수를, 해시 테이블은 포인터 추적 횟수를, 역색인은 비교해야 할 문서 수를 줄이기 위해 만들어졌습니다. 자료구조는 항상 “무엇이 비싼가”라는 질문의 답입니다.
